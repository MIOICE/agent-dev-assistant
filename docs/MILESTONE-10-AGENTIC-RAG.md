# 阶段 10：有界 Agentic RAG 证据研究

## 要解决的问题

原流程把整条需求拼成一个查询，只执行一次知识检索。它可以返回相关 Chunk，但存在三个业务问题：

- 一个复杂需求同时涉及业务规则、数据依赖、权限和性能，单个 Top-K 结果容易只覆盖其中一类。
- 没有显式记录“应该找什么”和“还缺什么”，方案生成看见几条相关文档就可能误以为证据充分。
- 首次查询没有命中时直接结束，无法根据需求上下文改写查询。

本阶段把固定 RAG 升级为有界的 Planner–Executor–Critic 证据研究循环。

## 实现链路

```text
结构化需求卡片
  -> EvidencePlanner 生成 1~5 个 EvidenceNeed
  -> Executor 按证据目标逐项调用 KnowledgeSearcher
  -> 混合检索器完成 BGE 语义召回、关键词召回、重排和置信度拒答
  -> 命中：保存稳定来源、分数和 Chunk ID，并移出待办集合
  -> 未命中：下一轮使用标题、模块和检索目的改写查询
  -> Critic 检查全部 required 目标是否获得可信证据
  -> 保存 EvidenceResearchReport，并把证据交给技术方案生成器
```

DeepSeek 模式使用结构化模型规划；Mock 模式使用规则规划。模型调用失败、JSON 不合法或违反 1 至 5 项、唯一 ID、字段长度等约束时，自动降级为规则规划并记录 `RULE_BASED_FALLBACK`。

## 有界自治

默认预算由服务端配置并在 Java 中校验：

- 最多 2 轮检索；
- 最多 6 次查询；
- 最终最多保留 8 条去重证据；
- 第二轮只处理上一轮未命中的目标；
- 达到预算立即停止，保留未解决证据 ID，不允许模型自行扩大权限或预算。

这里把灵活决策与确定性边界分开：模型决定应该检索哪些证据，Harness 决定何时调用、何时重试和何时停止。

## 可观察与可恢复

`EvidenceResearchReport` 随不可变 `WorkflowState` 快照保存，包括：

- 规划方式和证据需求；
- 每轮查询、命中结果 ID、最高分和是否满足；
- 去重后的最终证据；
- 未解决的证据缺口；
- 实际轮数、调用次数与配置预算。

工作台增加“Agentic RAG 证据研究”区域，直接展示这些信息。Trace 节点记录规划模式、轮数、查询数、证据数、充分性和缺口数，便于区分规划失败、检索失败和证据不足。

## 验证结果

- 验证首次未命中后只重试未解决目标，并使用业务上下文改写查询；
- 验证相同 Chunk 在多次查询中按 ID 去重并保留最高分；
- 验证必要证据全部覆盖后 `sufficient=true`；
- 验证查询预算耗尽后停止并暴露缺口；
- 全项目 93 个自动化测试通过。

## 面试复述

> 我发现单次 RAG 对复杂企业需求只能回答“搜到了什么”，不能回答“应该搜什么、还缺什么”。所以我实现了 Planner–Executor–Critic 证据研究：DeepSeek 把需求拆成 1 到 5 个结构化证据目标，Harness 逐项调用本地 BGE 混合检索，未命中时只对该目标做第二轮查询改写，最后用确定性 Critic 检查必需证据覆盖度。整个循环最多两轮、六次查询和八条证据，规划失败会降级到规则方案，所有计划、轨迹和缺口随工作流快照持久化并在前端展示。

## 简历可写版本

> 将单次 RAG 升级为 Planner–Executor–Critic 有界证据研究：由 DeepSeek 将需求拆分为 1 至 5 项可验证证据目标，Harness 在最多 2 轮、6 次查询预算内调用本地 BGE 混合检索，完成未命中查询改写、Chunk 去重与必要证据覆盖检查；支持模型规划失败规则降级，并将计划、检索轨迹和证据缺口随工作流快照持久化及可视化。

## 当前边界

- 当前 Critic 以检索结果通过置信度阈值作为“目标已覆盖”，尚未实现自然语言蕴含验证；命中不等同于证据一定支持最终结论。
- 方案生成器消费检索证据，但尚未对每条方案结论建立强制逐句引用。
- 查询改写当前只有一套确定性模板；后续可以比较 HyDE、多查询扩展和模型改写的效果与成本。
- Agentic RAG 尚未建立独立的证据规划金标集，本阶段的单元测试证明控制逻辑，不应冒充真实业务准确率提升。
