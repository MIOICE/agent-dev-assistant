# 里程碑 02：Agent Trace 与运行评测

## 为什么需要

普通后端接口只关心成功或失败，但 Agent 会经过需求分析、知识检索、方案生成和人工决策等多个节点。只看最终结果，很难判断是模型慢、检索没有命中，还是工作流规则导致反复澄清。

本轮实现了两层可观测能力：

- 单次 Trace：每个核心节点生成 `AgentTraceSpan`，记录统一 `traceId`、独立 `spanId`、状态、起止时间、耗时和统计属性。
- 聚合 Eval：从真实工作流快照、事件和 Span 计算首轮就绪率、平均澄清轮数、推荐值采纳率、完成率、失败率和平均节点耗时。

失败 Span 只记录异常类型，不保存密钥、完整 Prompt 或敏感业务数据。Trace 随 `WorkflowState` 一起保存，因此使用 MySQL 模式时重启后仍可查询。

## 面试时怎么复述

> 我没有把 Agent 当成一次普通大模型请求，而是按可观测工作流来设计。需求分析、RAG 检索、方案生成和驳回重生成分别记录 Span，使用同一个 workflowId 作为 traceId，保存节点状态、耗时和有限的安全属性。然后基于事件和 Span 聚合首轮就绪率、平均澄清轮数、推荐采纳率、任务完成率及节点耗时。这样遇到效果问题时，可以区分模型质量、检索质量和工作流设计问题，而不是只看一条最终回答。

如果面试官问与 OpenTelemetry 的关系：当前字段模型与 Trace/Span 概念对齐，能够完成项目内持久化和前端展示；下一步可以接 OpenTelemetry Collector，把 Span 导出到可观测平台。不要声称当前已经接入 Collector 或 Grafana。

## 接口

- `GET /api/workflows/{workflowId}/trace`：返回单次工作流全部 Span 与总耗时。
- `GET /api/workflows/metrics`：返回当前仓库内工作流聚合指标。

## 本轮验证

- `mvn clean test`：51 个自动化测试全部通过。
- Mock 端到端冒烟：完整需求生成 3 个成功 Span；模糊需求采用推荐值后保留原 `workflowId` 并进入 `WAITING_APPROVAL`。
- 聚合指标接口正确统计 2 条样例工作流、平均澄清轮数 0.5、推荐值采纳率 100%。
- 前端 JavaScript 语法检查通过，指标看板和调用轨迹资源加载成功。

## 本轮简历可写版本

项目名称：面向企业存量系统的需求开发 Agent

- 基于 Java 21、Spring Boot、Spring AI 与 DeepSeek 构建可恢复的 Agentic Workflow，串联结构化需求分析、本地 BGE RAG、技术方案生成和人工审批，并通过 MySQL 保存工作流快照与事件历史。
- 设计业务友好的结构化澄清机制，将问题划分为阻塞决策与默认假设，通过 Java 确定性策略限制问题数量并支持候选项选择、一键采用推荐值，降低非技术业务人员的使用成本。
- 为需求分析、RAG 检索、方案生成及驳回重生成节点建立持久化 Agent Trace，记录 traceId/spanId、执行状态、耗时与安全属性，并提供单次调用轨迹可视化。
- 基于真实工作流事件与 Span 构建运行评测看板，统计首轮就绪率、平均澄清轮数、推荐值采纳率、完成率、失败率及平均节点耗时；使用 JUnit 5、MockMvc 和 H2/MySQL 兼容测试验证核心链路。
