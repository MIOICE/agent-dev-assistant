# 项目累计面试话术

## 30 秒介绍

> 我做了一个面向企业存量系统的需求开发 Agent。业务人员输入自然语言需求后，系统会完成结构化分析、关键问题澄清、本地 BGE RAG、技术方案和人工审批。工程上实现了 MCP 工具治理、Agent Skills 语义路由、Trace 与评测，以及带 Checkpoint 的后台 Coding Agent。代码测试失败后可以在三次构建预算内自动修复，生成代码只在无网络 Docker 沙箱中运行，最终仍需二次人工审批。

## 2 分钟完整介绍

> 项目的背景是企业存量系统需求通常来自懂业务但不懂代码的人。传统做法需要产品或开发反复沟通，而且通用大模型不了解企业规范和数据库结构。我用 Java 21、Spring Boot、Spring AI 和 DeepSeek 搭建了一个可恢复的 Agentic Workflow。
>
> 第一阶段把自然语言转换为需求卡片，包括模块、验收标准、优先级、风险和待确认项。为了避免一次追问十几个技术问题，我把问题分成阻塞业务决策和 Agent 默认假设，每轮最多让业务人员确认四项。
>
> 需求明确后，DeepSeek 先把需求拆成业务规则、数据/API、安全和性能等证据目标，Harness 在两轮、六次查询预算内调用本地 BGE 混合检索；未命中目标会改写查询，必要证据仍不足时会显式保留缺口。检索证据进入技术方案后，Grounding 节点先把每条方案结论绑定到真实 Chunk，Claim–Evidence Critic 再批量判断支持、矛盾或证据不足，Java 对模型返回的结论 ID、证据 ID 和完整性做二次校验。方案必须人工审批，驳回后会重新执行绑定和审查。
>
> 工具层既支持 Spring AI 进程内 Tool Calling，也通过 MCP Streamable HTTP 对外提供业务文档和数据库元数据查询。我没有自动暴露全部工具，而是加入白名单、只读语义、参数限制、调用次数预算和隐私化审计。
>
> 为了排查 Agent 效果，我记录需求分析、RAG 和方案生成的 Trace，并统计首轮就绪率、澄清轮数、推荐采纳率、完成率和节点耗时。代码阶段还用标准 SKILL.md 拆分生成、失败修复、安全复核和导出可靠性方法，通过阶段过滤和本地 BGE 相似度按需加载正文。
>
> 技术方案审批后可以提交后台编码任务，接口返回 202，前端轮询任务进度。模型只能在限定目录生成少量 Java 文件，系统生成 Diff 和 SHA-256，再放入无网络、只读、限资源的 Docker 容器测试。如果编译或测试失败，修复 Agent 会读取错误证据并生成同路径修订版，最多构建三次。每次状态迁移都写入文件 Checkpoint，服务重启会恢复未完成任务；测试通过后仍要人工批准才输出到独立目录。目前累计有 114 个自动化测试。

## Agent Skills 与渐进式加载

> 我把代码生成、失败修复、安全复核和导出可靠性写成四个标准 SKILL.md。应用先按 GENERATION 或 REPAIR 阶段过滤，保留阶段必选技能，再用本地 BGE 计算任务与可选技能描述的余弦相似度，以阈值和 Top-N 预算选择正文。这叫渐进式披露，可以减少无关上下文。每次激活和路由分数都会进入任务 Checkpoint 时间线。

## 为什么技能路由不用模型直接决定

> 大模型直接选 Skill 灵活，但又增加一次模型调用、延迟和不确定性。我这里复用了本地 BGE：阶段状态机先给硬边界，向量检索再做软选择，基础技能始终保留，可选技能受阈值和数量预算限制。它成本低、结果可解释，也方便离线评测。后续技能规模更大时可以比较向量路由、模型路由和混合路由的准确率。

## 如何防止恶意 Skill 或供应链篡改

> 首先，Skill 的 allowed-tools 只是声明，必须属于宿主白名单，不能授予权限。其次，应用启动时对完整 SKILL.md 计算 SHA-256，并与代码评审后提交的可信清单逐项比对；摘要不一致、清单缺项、非法阶段或未知工具都会 fail-fast。SHA-256 清单只能证明内容与评审版本一致，不等于数字签名；生产环境还需要签名制品和可信发布链。

## Skills 和普通 Prompt 模板有什么区别

> Prompt 模板通常和某个模型调用写死在一起；Skill 是可发现、可路由、可复用的能力包，元数据负责选择，正文负责具体方法，还可以扩展脚本、参考资料和输出资产。这个项目目前使用的是轻量 SKILL.md，没有为了凑技术引入无用目录。底层仍通过 Spring AI 调模型，所以 Skill 是上下文工程层，不是新的模型框架。

## Skill 声明工具会不会自动获得权限

> 不会。allowed-tools 只是需求声明，不能成为授权来源，否则第三方 Skill 写一句工具名就能提权。项目中真正权限仍由服务端 MCP 白名单、文件路径和危险 API 校验、固定 Docker 命令、自治预算以及人工审批控制。我把“如何完成任务”和“允许执行什么”明确分层。

## 为什么选择 Agentic Workflow，而不是完全自主 Agent

> 企业需求开发包含澄清、检索、方案、审批和执行等明确阶段，高风险节点也必须人工确认，所以我选择确定性状态机作为骨架，让模型只负责语义理解和内容生成。这样状态可恢复、步骤可测试、权限边界也更清楚。完全自主循环灵活，但更难控制成本、重试和副作用。

## 什么才算 Agent

> 我的理解是模型本身不是 Agent。Agent 至少包含模型、指令、工具、状态、执行循环和权限边界。这个项目里的模型负责需求分析、方案和代码计划；工作流服务负责推进状态；RAG 和 MCP 提供外部知识与工具；MySQL 保存状态；人工审批和自治预算控制副作用。

## 为什么选 Spring AI，不选 LangChain4j

> 项目主线是 Java 后端和 Spring Boot，Spring AI 与配置管理、依赖注入、结构化输出、Tool Calling、向量库和 MCP Starter 集成更自然。我选择它是为了减少框架拼接成本，并不是认为 LangChain4j 不好。如果团队已有 LangChain4j 资产，也可以保留领域接口，只替换具体适配器。

## 结构化输出与确定性校验

> 我先用模型把输出约束到 Java Record 和 JSON Schema，再用 Java 校验器检查优先级、空集合、阻塞问题数量和推荐选项。Schema 解决格式问题，确定性校验解决业务规则问题。不能把安全和流程正确性完全交给 Prompt。

## 为什么追问不能太多

> 用户是懂业务但不懂代码的人。如果把文件格式、分页阈值、重试次数等全部抛给用户，Agent 只是把开发工作转嫁给业务人员。我只让会改变业务结果、权限范围或不可逆影响的问题阻塞流程，其余技术选择由 Agent 给默认值并在方案中透明展示。

## RAG 链路

> 文档先按Markdown标题层级分块，用本地BGE中文模型向量化。向量和Chunk元数据会保存为本地磁盘快照，下一次启动通过SHA-256清单判断直接复用还是增量更新。查询时同时做向量召回和全语料关键词召回，再按页面标题、模块、关键词和二元词覆盖率计算综合分，限制同一来源最多两个Chunk，并用最终置信度门槛拒答。项目用Hit@K、Precision@K、MRR和无关问题拒绝率做离线评测，而不是凭肉眼判断效果。

## 为什么把单次 RAG 升级成 Agentic RAG

> 一个需求往往同时需要业务规则、表和接口依赖、权限边界与性能约束。把整段需求只检索一次，Top-K 容易被某一类文档占满，不能知道还有哪类证据没找到。我增加了 Planner–Executor–Critic：Planner 生成结构化证据清单，Executor 逐项检索并对未命中项改写查询，Critic 检查必要证据覆盖度。它不是为了多调用模型，而是让“找什么、找到了什么、还缺什么”可观察。

## 它为什么算 Agent，而不只是循环搜索

> DeepSeek 会根据当前需求动态决定证据目标，Harness 根据每次检索结果决定结束还是进入下一轮，后续技术方案会消费这些证据；同时工作流保存计划、状态、动作轨迹和缺口。因此它具备模型决策、工具使用、状态和反馈循环。外层仍是确定性 Agentic Workflow，因为企业场景更重视可控性，而不是追求完全自主。

## 如何防止 Agentic RAG 无限循环和成本失控

> Java Harness 硬限制最多两轮、六次查询和八条最终证据，不接受模型扩大预算。每个已命中的目标从待办集合移除，第二轮只处理未命中项；达到轮数或查询预算会立即停止，并把未解决 ID 写入工作流快照。这样即使模型规划不理想，延迟和计算成本也有上界。

## 证据充分性为什么不用另一个模型判断

> 当前先采用可解释的确定性 Critic：底层检索已经做综合分阈值和无关问题拒答，所有必需证据目标至少返回一条过阈值结果才算充分。优点是稳定、便于测试且不增加调用成本；局限是“命中”不一定等于内容真正支持结论。生产下一步可以增加 NLI 或模型判定，但仍需引用校验和离线金标评测。

## DeepSeek 规划失败怎么办

> 规划输出先经过 Spring AI Schema 映射和 Java Record 校验，限制 1 至 5 项、ID 唯一及字段长度。调用失败、JSON 不合法或违反约束时，系统降级到规则规划器，按需求关键词补充业务、数据、安全和性能证据目标，并把 `RULE_BASED_FALLBACK` 写入轨迹。降级保证流程可用，也不会伪装成模型成功。

## 方案证据绑定是怎么做的

> 技术方案生成后，我把摘要、后端、数据库、API、安全、性能、测试和回滚拆成原子结论。Grounding 服务根据证据计划的类别和实际查询结果建立结论到 Chunk ID 的映射，并再次检查 ID 必须存在于最终去重证据集合。待确认项统一标记为 ASSUMPTION，专项证据没有命中则标为 UNSUPPORTED，最终计算排除假设后的证据关联率。驳回重生成后会重新执行绑定，避免旧引用跟着新方案继续使用。

## 为什么“已关联证据”不等于“事实正确”

> RAG 的相似度和证据目标命中只能说明这份资料与结论相关，不能证明资料在逻辑上支持结论。因此 Grounding 状态仍叫 EVIDENCE_LINKED。后续独立 Critic 会判断支持、矛盾或证据不足，但它本身也是模型，仍可能误判，所以结果是审批信号而不是事实证明。当前没有 claim–evidence 人工金标准确率，我只如实展示分类、置信度和引用，并保留最终人工审批。

## Claim–Evidence Critic 是怎么做的

> Grounding 完成后，我把全部原子结论和一份去重证据字典放进一次 DeepSeek 结构化调用，而不是每条结论单独调用。模型为每个 claimId 返回 SUPPORTED、CONTRADICTED 或 INSUFFICIENT、置信度、理由和引用 ID。Java Assembler 再用 Grounding 里的稳定 claimId 和最终 Chunk 集合做白名单交集：未知结论被忽略，非法证据被删除，缺失结果标成 NOT_EVALUATED，支持或矛盾但没有合法引用则降级为证据不足。这样模型负责语义判断，程序负责身份、完整性和安全边界。

## 为什么采用一次批量调用

> 多条方案结论经常共享相同证据。逐条调用会重复发送 Chunk，成本和延迟随结论数线性上升，也更难保持判定口径一致。我先构建唯一 evidenceId 字典，每条结论只携带允许引用的 ID，再批量返回结构化结果。代价是单次上下文更长，所以生产环境需要按 Token 预算分批；当前方案规模受控，一次批处理更合适。

## 模型审查失败怎么办

> 不会把失败包装成“全部通过”。DeepSeek 超时、JSON 不合法或 Schema 映射失败时，系统降级为 RULE_BASED_FALLBACK：保留原有证据绑定，但所有事实性结论显示待人工复核，工作流仍可进入审批。Mock 模式同样使用 RULE_BASED_NOT_EVALUATED，方便演示完整流程，又不伪造语义判断结果。

## Claim–Evidence Critic 怎么评测

> 我自建了 12 条人工标注的合成 MES 业务样例，支持、矛盾、证据不足各 4 条，覆盖导出权限、大数据量、逻辑删除、状态流转和无法从证据推导具体参数等场景。评测复用生产 Critic，一次批量调用后比较金标与预测，输出 Coverage、Accuracy、每类 Recall、Macro Recall 和混淆矩阵。它不是只测 JSON 能否解析，而是测语义分类结果。

## 为什么 Accuracy 之外还要 Coverage

> 只有被判为支持、矛盾或不足的样例才进入 Accuracy 分母；模型漏项、调用失败或 Mock 模式会得到 NOT_EVALUATED。如果只看 Accuracy，模型可以漏掉困难题后在少量容易题上拿高分，所以我让漏答降低 Coverage 和对应类别 Recall。这样可以同时看“答了多少”和“答对多少”。

## 这 12 条评测能证明生产准确率吗

> 不能。它们是公开仓库可提交的合成回归样例，主要验证评测链路、提示词变化和模型版本回归。真实生产前还需要从经过授权的脱敏历史案例中抽样，由业务和研发双人标注，并划分开发集与盲测集。我不会把自动化测试通过数或这 12 条小样本包装成生产准确率。

## 为什么证据绑定放在方案生成之后

> 检索前只能规划要找的证据，不知道模型最终会写出哪些具体结论；方案生成后才能逐条检查引用和假设。把它做成独立节点还有两个好处：一是可以单独记录 Trace 和关联率，二是方案被人工驳回并重新生成时能够重新绑定，而不是复用可能已经过期的引用。

## 增量向量索引如何实现

> 我为每个Chunk的ID、正文和元数据计算SHA-256，并在磁盘清单中保存`chunkId -> fingerprint`。启动时将当前清单与旧清单做集合差分：不存在的是新增，指纹变化的是更新，旧清单独有的是删除。系统先加载旧向量快照，只对新增和更新Chunk调用Embedding，对更新和删除ID执行delete，然后原子保存新快照与清单。语料完全不变时3311个向量全部复用，重新Embedding数量为0。

## 为什么现阶段没有直接使用Qdrant

> 当前项目是单机求职Demo，主要问题是重复向量化，而不是海量数据、分布式检索或高并发。`SimpleVectorStore`磁盘快照加增量清单已经让两次热启动稳定在14.63至15.36秒，相比原约36秒缩短约58%，同时不增加外部服务部署成本。我把检索调用与索引管理分层，后续需要过滤查询、多实例和在线扩容时再替换为Qdrant或PGVector。技术选型应解决当前瓶颈，而不是为了简历堆组件。

## 如何保证索引缓存一致性

> 语料指纹解决内容变化，显式`modelId`解决Embedding模型或预处理规则变化；Schema版本变化也会判定旧索引不兼容。快照和清单使用临时文件加原子替换，损坏时不会继续提供不可信结果，而是进入`RECOVERED_REBUILD`全量重建。当前属于单进程一致性，生产多实例还需要分布式锁、索引版本和蓝绿切换。

## 向量快照是否可以公开

> 不可以。Embedding不是可靠匿名化手段，而且`SimpleVectorStore`的JSON快照还会保存Chunk文本和元数据。项目只把索引代码提交Git，快照留在忽略目录或Docker私有Volume中。生产环境还需要磁盘加密、租户授权、备份策略和索引删除审计。

## 为什么要做混合检索

> 企业文档里有控制器名、接口名、表名和页面名称等精确词。纯向量检索擅长语义相近，但可能把“生产订单列表”召回到“订单排程”；纯关键词又不理解同义表达。我把 BGE 向量候选与关键词候选合并后重排：精确标题即使没进向量 Top-K 也能被补回，同时语义查询仍由向量负责。实测生产订单页面从向量候选第 3 位提升到综合排序第 1 位。

## 为什么按标题分块，不直接固定字数

> MES 页面文档天然按字段、接口、服务和数据表分节。只按固定字数截断可能把标题与正文拆开，检索结果也缺少上下文。我先按 H1 到 H4 建立标题链，再对超长章节二次分块，并把“模块、页面、标题链”作为检索前缀和元数据。这样引用能定位到具体章节，面试时也能解释为什么这个 Chunk 被召回。

## 私有业务文档如何防止泄漏

> 外部知识库必须显式开启，加载器只读扫描允许列表内的 Markdown，限制文件数量和单文件大小，不跟随符号链接，并过滤目录节点。内容进入索引前会替换疑似密钥、IP、邮箱、手机号和本地绝对路径。Git 只提交加载逻辑，不提交原始语料、本地根路径或写死的私有评测问题。这里的正则脱敏是基础防线，不代表完整 DLP；生产环境还需要文档分级、租户权限、密钥扫描和审计。

## RAG 指标怎么解释

> 当前本机语料共加载 240 份文档，其中 237 份是外部 MES 资料，生成 3311 个 Chunk；144 份不在允许范围或不满足规则的 Markdown 被跳过，2 份在入库前触发脱敏。12 条自动评测全部通过，Hit@K、MRR 和无关问题拒绝率都是 100%，Precision@K 是 55%。Precision 较低主要因为 Top-4 会返回同一正确文档的多个相关章节，不能包装成 100% 精准；这组数据适合证明回归与阈值选择，还不是生产金标集。下一步应让业务专家建立独立问题—证据标注集，并增加 nDCG、延迟与成本指标。

## RAG 与 Tool Calling 的区别

> RAG 是知识注入模式，重点是找到相关资料并进入上下文；Tool Calling 是模型在执行过程中选择某个能力。项目同时使用：主工作流固定执行 RAG，模型还可以按需要调用业务文档和数据库元数据工具。

## MCP 与 Function Calling 的区别

> Function Calling 主要描述模型如何产出结构化工具调用；MCP 解决客户端和外部工具服务之间如何发现能力、协商协议和交换结果。项目内部为低延迟使用 Spring AI `@Tool`，对外通过 MCP Streamable HTTP 复用同类能力，没有让应用通过网络调用自己。

## MCP 安全怎么做

> 只读提示只是元数据，不是真正的权限控制。我关闭了本地工具自动转换，只暴露两个显式 `@McpTool`；服务端还有白名单、500 字参数限制、单轮和单工具调用上限、默认本机监听，以及不记录 Prompt 和结果正文的审计。生产环境仍需要 OAuth、租户身份和持久化审计。

## Trace 与 Evals

> 每个核心节点保存统一 traceId、独立 spanId、状态、耗时和有限属性。聚合层再根据事件和 Span 计算首轮就绪率、平均澄清轮数、推荐值采纳率、完成率、失败率和节点耗时。这样能够区分模型问题、检索问题和流程问题。当前是项目内 Trace，还没有冒充已经接入 OpenTelemetry Collector。

## 为什么 Agent 评测还需要版本和发布门禁

> 单次跑出一个准确率只能描述当时的结果，无法判断更换模型或修改 Prompt 后是否退化。我把每次评测保存为不可变 Eval Run，记录 AI 模式、模型 ID、Prompt 版本、数据集版本和内容 SHA-256。门禁先检查 Coverage、Accuracy、Macro Recall 和最低分类 Recall 的绝对阈值，再与最近一次通过的基线比较；任何指标下降超过 8 个百分点都不能发布。Mock 没有执行语义判断，因此状态是 NOT_EVALUATED，既不会通过门禁，也不会成为基线。

## 为什么基线选择“最近一次通过”，而不是“最近一次运行”

> 如果失败运行自动成为下一次基线，模型连续退化时，每次只下降一点就可能掩盖累计问题。项目只把通过绝对阈值和回归检查的运行作为候选基线，失败和未评估结果只保留用于审计，不改变质量参照。当前基线仍是自动选择，生产系统还应增加人工批准和环境维度。

## 为什么运行评测使用 POST

> 真实模型评测会消耗额度并写入运行记录，因此不是安全、幂等的读取操作。正式运行只使用 POST；历史、最近运行以及兼容结果端点都只通过 GET 读取已保存数据。这样 HTTP 语义与实际副作用一致，也避免浏览器预加载或爬虫意外触发模型调用。

## 如何避免业务用户一次回答很多问题

> 我没有简单把模型生成的问题全部展示出来，而是在模型后增加确定性问题路由器。路由器先把线程池、索引、分页和重试等技术实现问题转为Agent假设，再按不可逆操作、权限、数据范围和普通偏好计算优先级，每轮只展示最高价值的三项业务决策。每个问题都带“为什么问”和“会影响什么”，并提供推荐答案；用户可以逐项选择，也可以一次接受推荐值。

## 为什么不用模型自己决定哪些问题重要

> 模型适合理解自然语言，但不能独自控制是否跳过权限或删除确认。我让模型产生候选问题和解释，Java策略负责技术词识别、风险排序、数量预算和安全兜底。存在推荐值的低优先问题可以转成显式假设，完全没有安全默认值的问题即使超过三问也不能静默忽略。这是语义判断和确定性安全约束的分工。

## 少问问题会不会导致需求信息不足

> 少问不等于丢掉问题。被Agent处理的项目会进入assumptions并展示给用户，后续技术方案和人工审批仍能复核；高风险、无默认值的问题继续保持阻塞。工作流每次收到答案后会用原workflowId重新分析，因此后续仍可根据新信息生成下一轮问题。这相当于渐进式披露，而不是一次性问卷。

## 为什么不能直接在宿主机运行生成代码

> 文件夹不是安全边界。即使限制路径，生成代码仍可能读取环境变量、访问网络或操作其他文件。因此项目禁止宿主执行，只允许固定 Docker 命令。容器无网络、根文件系统只读，源码和 Maven 仓库只读挂载，并限制 CPU、内存、PID、时间和临时磁盘；Docker 不可用就失败，不做不安全降级。

## 什么是 Autonomy Budget

> 自治预算限制 Agent 最多能生成多少文件和字节、调用多少次构建、占用多少沙箱时间、使用多少 CPU、内存和进程。当前代码任务最多生成 6 个文件、100KB 内容、执行 3 次构建和 180 秒沙箱时间。它不提升模型正确率，但能限制错误规划的成本和影响范围。

## 自动修复循环怎么设计

> 我没有让模型无限自我反思，而是采用 Generate–Test–Repair 循环。Docker 只有明确返回编译或测试失败时才进入修复；修复 Agent 获得上一版完整文件和截断后的失败日志，输出仍要经过结构化 Schema 和 Java 安全策略。修复不能新增、删除或重命名文件，也不能删除测试或放宽断言。最多测试三次，仍失败就进入 FAILED。这叫有界自治，而不是无限重试。

## 为什么代码任务要异步

> 模型生成和容器测试可能持续几十秒，如果占用 HTTP 请求线程，会造成超时、连接浪费和很差的用户体验。创建接口只负责校验并持久化 QUEUED 快照，然后返回 202；固定大小线程池负责后台执行，队列也有容量上限。前端通过任务 ID 轮询状态，后续可以无缝替换成 SSE 或消息队列。

## Checkpoint 与普通日志有什么区别

> 日志主要用于观察发生了什么，Checkpoint 保存继续执行所需的完整状态，例如已审批的工作流输入快照、阶段、补丁、构建次数、累计沙箱耗时、修复轮数、验证结果和事件。项目用 JSON 快照落盘，并通过临时文件加原子替换避免写到一半。应用启动后扫描未完成状态并重新调度，因此恢复不依赖原工作流仓库仍在线。

## 恢复执行如何避免无限消耗

> 构建次数会在真正启动 Docker 之前写入 Checkpoint，所以进程如果在调用期间崩溃，这次预算不会在重启后被返还。恢复时沿用已消耗的构建次数和时间，并使用新的隔离工作区，不覆盖执行上一次的不完整目录。这是保守的至少一次调度语义；因为人工发布前没有外部业务副作用，所以重复生成不会影响真实系统。

## 为什么 Docker 不可用时不自动修复

> 自动修复只适合代码导致的编译或测试失败。Docker 未启动、依赖仓库缺失、路径越界或安全策略拒绝都不是代码缺陷，继续调用模型只会浪费预算，甚至诱导模型绕过安全边界。因此这些异常会直接安全停止并保留 Checkpoint。

## 为什么测试通过后还要审批

> 自动化测试只能证明覆盖到的行为，没有证明需求、安全和代码质量一定正确。因此技术方案审批确认“怎么做”，代码审批确认“实际做了什么”。发布前还会重新计算 SHA-256，避免测试后文件被替换。

## 项目最难的三个点

> 第一是让业务人员少回答问题，所以设计了阻塞决策与默认假设。第二是处理模型不确定性，用结构化输出、Java 校验、状态机、Trace 和评测把不可控部分包起来。第三是代码执行安全，最终放弃宿主进程执行，改成无网络、只读和限资源的容器，并保留人工审批。

## 失败与恢复

> 需求分析、检索或方案生成失败时，工作流进入 FAILED 并保存已有上下文，用户可以在同一 workflowId 上重试。代码阶段保存完整文件 Checkpoint，测试失败会在预算内自动修复；应用启动后自动恢复 QUEUED、GENERATING、VERIFYING 和 REPAIRING 任务。达到预算或遇到基础设施错误后安全停止，绝不会绕过测试发布。

## 当前真实边界

- 数据库工具查询的是演示元数据目录，不读取真实业务行数据。
- 代码只生成到独立演示工程，不直接修改真实存量项目。
- 当前电脑未安装或未配置 Docker CLI，因此容器成功链路尚未在本机完成冒烟；代码明确禁止回退到宿主执行。
- MCP 暂无 OAuth 和租户级授权。
- Trace 尚未导出到 OpenTelemetry Collector。
- 文件 Checkpoint 解决的是单实例恢复，尚未实现 Redis/消息队列、多实例任务租约和分布式抢占。
- 真实 Git 分支与 Pull Request 尚未实现。
- 外部MES语料仍在启动时读取和分块，但向量使用单机磁盘快照与Chunk级增量更新；3311个Chunk热启动全部复用，两次实测14.63至15.36秒，相比原约36秒缩短约58%。
- 当前不是Qdrant/PGVector等独立向量数据库，尚未实现多实例索引锁、在线版本切换、加密快照和多租户检索权限。
- 自动生成的外部语料评测题主要验证标题可检索性，不是独立人工金标集；公开仓库不包含原始业务文档和私有问法。

面试时主动说出边界不会减分，反而说明你理解 Demo、生产系统和安全声明之间的区别。
