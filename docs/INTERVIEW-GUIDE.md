# 项目累计面试话术

## 30 秒介绍

> 我做了一个面向企业存量系统的需求开发 Agent。业务人员输入自然语言需求后，系统会完成结构化需求分析、关键问题澄清、本地 BGE RAG 业务知识检索、技术方案生成和人工审批。工程上还实现了 MCP 标准工具服务、工具白名单和审计、Agent Trace 与效果指标，以及受自治预算约束的代码补丁生成。生成代码只在无网络 Docker 沙箱中离线测试，测试通过后还要第二次人工审批，不会直接修改真实仓库。

## 2 分钟完整介绍

> 项目的背景是企业存量系统需求通常来自懂业务但不懂代码的人。传统做法需要产品或开发反复沟通，而且通用大模型不了解企业规范和数据库结构。我用 Java 21、Spring Boot、Spring AI 和 DeepSeek 搭建了一个可恢复的 Agentic Workflow。
>
> 第一阶段把自然语言转换为需求卡片，包括模块、验收标准、优先级、风险和待确认项。为了避免一次追问十几个技术问题，我把问题分成阻塞业务决策和 Agent 默认假设，每轮最多让业务人员确认四项。
>
> 需求明确后，系统用本地 BGE 模型对企业文档做分块、向量检索和来源引用，再生成包含接口、安全、性能、测试和回滚的技术方案。方案必须人工审批，驳回意见会进入下一次生成。
>
> 工具层既支持 Spring AI 进程内 Tool Calling，也通过 MCP Streamable HTTP 对外提供业务文档和数据库元数据查询。我没有自动暴露全部工具，而是加入白名单、只读语义、参数限制、调用次数预算和隐私化审计。
>
> 为了排查 Agent 效果，我记录需求分析、RAG 和方案生成的 Trace，并统计首轮就绪率、澄清轮数、推荐采纳率、完成率和节点耗时。
>
> 技术方案审批后可以进入安全编码阶段。模型只能在限定目录生成少量 Java 文件，系统生成 Diff 和 SHA-256，然后放入无网络、只读、限资源的 Docker 容器离线测试。测试通过后仍要人工批准才输出到独立目录。目前累计有 63 个自动化测试。

## 为什么选择 Agentic Workflow，而不是完全自主 Agent

> 企业需求开发包含澄清、检索、方案、审批和执行等明确阶段，高风险节点也必须人工确认，所以我选择确定性状态机作为骨架，让模型只负责语义理解和内容生成。这样状态可恢复、步骤可测试、权限边界也更清楚。完全自主循环灵活，但更难控制成本、重试和副作用。

## 什么才算 Agent

> 我的理解是模型本身不是 Agent。Agent 至少包含模型、指令、工具、状态、执行循环和权限边界。这个项目里的模型负责需求分析、方案和代码计划；工作流服务负责推进状态；RAG 和 MCP 提供外部知识与工具；MySQL 保存状态；人工审批和自治预算控制副作用。

## 为什么选 Spring AI，不选 LangChain4j

> 项目主线是 Java 后端和 Spring Boot，Spring AI 与配置管理、依赖注入、结构化输出、Tool Calling、向量库和 MCP Starter 集成更自然。我选择它是为了减少框架拼接成本，并不是认为 LangChain4j 不好。如果团队已有 LangChain4j 资产，也可以保留领域接口，只替换具体适配器。

## 结构化输出与确定性校验

> 我先用模型把输出约束到 Java Record 和 JSON Schema，再用 Java 校验器检查优先级、空集合、阻塞问题数量和推荐选项。Schema 解决格式问题，确定性校验解决业务规则问题。不能把安全和流程正确性完全交给 Prompt。

## 为什么追问不能太多

> 用户是懂业务但不懂代码的人。如果把文件格式、分页阈值、重试次数等全部抛给用户，Agent 只是把开发工作转嫁给业务人员。我只让会改变业务结果、权限范围或不可逆影响的问题阻塞流程，其余技术选择由 Agent 给默认值并在方案中透明展示。

## RAG 链路

> 文档先解析并分块，用本地 BGE 中文模型向量化后写入向量存储。查询时取 Top-K 相似片段，将内容、来源 ID、Chunk 和分数一起放入模型上下文。项目还有自建评测集，使用 Hit@K、Precision@K、MRR 和无关问题拒绝率比较阈值，而不是凭肉眼判断检索好不好。

## RAG 与 Tool Calling 的区别

> RAG 是知识注入模式，重点是找到相关资料并进入上下文；Tool Calling 是模型在执行过程中选择某个能力。项目同时使用：主工作流固定执行 RAG，模型还可以按需要调用业务文档和数据库元数据工具。

## MCP 与 Function Calling 的区别

> Function Calling 主要描述模型如何产出结构化工具调用；MCP 解决客户端和外部工具服务之间如何发现能力、协商协议和交换结果。项目内部为低延迟使用 Spring AI `@Tool`，对外通过 MCP Streamable HTTP 复用同类能力，没有让应用通过网络调用自己。

## MCP 安全怎么做

> 只读提示只是元数据，不是真正的权限控制。我关闭了本地工具自动转换，只暴露两个显式 `@McpTool`；服务端还有白名单、500 字参数限制、单轮和单工具调用上限、默认本机监听，以及不记录 Prompt 和结果正文的审计。生产环境仍需要 OAuth、租户身份和持久化审计。

## Trace 与 Evals

> 每个核心节点保存统一 traceId、独立 spanId、状态、耗时和有限属性。聚合层再根据事件和 Span 计算首轮就绪率、平均澄清轮数、推荐值采纳率、完成率、失败率和节点耗时。这样能够区分模型问题、检索问题和流程问题。当前是项目内 Trace，还没有冒充已经接入 OpenTelemetry Collector。

## 为什么不能直接在宿主机运行生成代码

> 文件夹不是安全边界。即使限制路径，生成代码仍可能读取环境变量、访问网络或操作其他文件。因此项目禁止宿主执行，只允许固定 Docker 命令。容器无网络、根文件系统只读，源码和 Maven 仓库只读挂载，并限制 CPU、内存、PID、时间和临时磁盘；Docker 不可用就失败，不做不安全降级。

## 什么是 Autonomy Budget

> 自治预算限制 Agent 最多能生成多少文件和字节、调用多少次构建、运行多久、使用多少 CPU、内存和进程。它不提升模型正确率，但能限制错误规划的成本和影响范围，是生产 Agent 的重要安全措施。

## 为什么测试通过后还要审批

> 自动化测试只能证明覆盖到的行为，没有证明需求、安全和代码质量一定正确。因此技术方案审批确认“怎么做”，代码审批确认“实际做了什么”。发布前还会重新计算 SHA-256，避免测试后文件被替换。

## 项目最难的三个点

> 第一是让业务人员少回答问题，所以设计了阻塞决策与默认假设。第二是处理模型不确定性，用结构化输出、Java 校验、状态机、Trace 和评测把不可控部分包起来。第三是代码执行安全，最终放弃宿主进程执行，改成无网络、只读和限资源的容器，并保留人工审批。

## 失败与恢复

> 需求分析、检索或方案生成失败时，工作流进入 FAILED 并保存已有上下文，用户可以在同一 workflowId 上重试。代码阶段测试失败则禁止发布。当前需求工作流能通过 MySQL 恢复，但代码任务还是内存状态，下一步会把代码任务和检查点持久化。

## 当前真实边界

- 数据库工具查询的是演示元数据目录，不读取真实业务行数据。
- 代码只生成到独立演示工程，不直接修改真实存量项目。
- 当前电脑未安装或未配置 Docker CLI，因此容器成功链路尚未在本机完成冒烟；代码明确禁止回退到宿主执行。
- MCP 暂无 OAuth 和租户级授权。
- Trace 尚未导出到 OpenTelemetry Collector。
- Redis、自动多轮修复、真实 Git 分支与 Pull Request 尚未实现。

面试时主动说出边界不会减分，反而说明你理解 Demo、生产系统和安全声明之间的区别。
