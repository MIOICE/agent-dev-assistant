# 项目累计面试话术

## 30 秒介绍

> 我做了一个面向企业存量系统的需求开发 Agent。业务人员输入自然语言需求后，系统会完成结构化分析、关键问题澄清、本地 BGE RAG、技术方案和人工审批。工程上实现了 MCP 工具治理、Agent Skills 语义路由、Trace 与评测，以及带 Checkpoint 的后台 Coding Agent。代码测试失败后可以在三次构建预算内自动修复，生成代码只在无网络 Docker 沙箱中运行，最终仍需二次人工审批。

## 2 分钟完整介绍

> 项目的背景是企业存量系统需求通常来自懂业务但不懂代码的人。传统做法需要产品或开发反复沟通，而且通用大模型不了解企业规范和数据库结构。我用 Java 21、Spring Boot、Spring AI 和 DeepSeek 搭建了一个可恢复的 Agentic Workflow。
>
> 第一阶段把自然语言转换为需求卡片，包括模块、验收标准、优先级、风险和待确认项。为了避免一次追问十几个技术问题，我把问题分成阻塞业务决策和 Agent 默认假设，每轮最多让业务人员确认四项。
>
> 需求明确后，系统用本地 BGE 模型对企业文档做分块、向量检索和来源引用，再生成包含接口、安全、性能、测试和回滚的技术方案。方案必须人工审批，驳回意见会进入下一次生成。
>
> 工具层既支持 Spring AI 进程内 Tool Calling，也通过 MCP Streamable HTTP 对外提供业务文档和数据库元数据查询。我没有自动暴露全部工具，而是加入白名单、只读语义、参数限制、调用次数预算和隐私化审计。
>
> 为了排查 Agent 效果，我记录需求分析、RAG 和方案生成的 Trace，并统计首轮就绪率、澄清轮数、推荐采纳率、完成率和节点耗时。代码阶段还用标准 SKILL.md 拆分生成、失败修复、安全复核和导出可靠性方法，通过阶段过滤和本地 BGE 相似度按需加载正文。
>
> 技术方案审批后可以提交后台编码任务，接口返回 202，前端轮询任务进度。模型只能在限定目录生成少量 Java 文件，系统生成 Diff 和 SHA-256，再放入无网络、只读、限资源的 Docker 容器测试。如果编译或测试失败，修复 Agent 会读取错误证据并生成同路径修订版，最多构建三次。每次状态迁移都写入文件 Checkpoint，服务重启会恢复未完成任务；测试通过后仍要人工批准才输出到独立目录。目前累计有 76 个自动化测试。

## Agent Skills 与渐进式加载

> 我把代码生成、失败修复、安全复核和导出可靠性写成四个标准 SKILL.md。应用先按 GENERATION 或 REPAIR 阶段过滤，保留阶段必选技能，再用本地 BGE 计算任务与可选技能描述的余弦相似度，以阈值和 Top-N 预算选择正文。这叫渐进式披露，可以减少无关上下文。每次激活和路由分数都会进入任务 Checkpoint 时间线。

## 为什么技能路由不用模型直接决定

> 大模型直接选 Skill 灵活，但又增加一次模型调用、延迟和不确定性。我这里复用了本地 BGE：阶段状态机先给硬边界，向量检索再做软选择，基础技能始终保留，可选技能受阈值和数量预算限制。它成本低、结果可解释，也方便离线评测。后续技能规模更大时可以比较向量路由、模型路由和混合路由的准确率。

## 如何防止恶意 Skill 或供应链篡改

> 首先，Skill 的 allowed-tools 只是声明，必须属于宿主白名单，不能授予权限。其次，应用启动时对完整 SKILL.md 计算 SHA-256，并与代码评审后提交的可信清单逐项比对；摘要不一致、清单缺项、非法阶段或未知工具都会 fail-fast。SHA-256 清单只能证明内容与评审版本一致，不等于数字签名；生产环境还需要签名制品和可信发布链。

## Skills 和普通 Prompt 模板有什么区别

> Prompt 模板通常和某个模型调用写死在一起；Skill 是可发现、可路由、可复用的能力包，元数据负责选择，正文负责具体方法，还可以扩展脚本、参考资料和输出资产。这个项目目前使用的是轻量 SKILL.md，没有为了凑技术引入无用目录。底层仍通过 Spring AI 调模型，所以 Skill 是上下文工程层，不是新的模型框架。

## Skill 声明工具会不会自动获得权限

> 不会。allowed-tools 只是需求声明，不能成为授权来源，否则第三方 Skill 写一句工具名就能提权。项目中真正权限仍由服务端 MCP 白名单、文件路径和危险 API 校验、固定 Docker 命令、自治预算以及人工审批控制。我把“如何完成任务”和“允许执行什么”明确分层。

## 为什么选择 Agentic Workflow，而不是完全自主 Agent

> 企业需求开发包含澄清、检索、方案、审批和执行等明确阶段，高风险节点也必须人工确认，所以我选择确定性状态机作为骨架，让模型只负责语义理解和内容生成。这样状态可恢复、步骤可测试、权限边界也更清楚。完全自主循环灵活，但更难控制成本、重试和副作用。

## 什么才算 Agent

> 我的理解是模型本身不是 Agent。Agent 至少包含模型、指令、工具、状态、执行循环和权限边界。这个项目里的模型负责需求分析、方案和代码计划；工作流服务负责推进状态；RAG 和 MCP 提供外部知识与工具；MySQL 保存状态；人工审批和自治预算控制副作用。

## 为什么选 Spring AI，不选 LangChain4j

> 项目主线是 Java 后端和 Spring Boot，Spring AI 与配置管理、依赖注入、结构化输出、Tool Calling、向量库和 MCP Starter 集成更自然。我选择它是为了减少框架拼接成本，并不是认为 LangChain4j 不好。如果团队已有 LangChain4j 资产，也可以保留领域接口，只替换具体适配器。

## 结构化输出与确定性校验

> 我先用模型把输出约束到 Java Record 和 JSON Schema，再用 Java 校验器检查优先级、空集合、阻塞问题数量和推荐选项。Schema 解决格式问题，确定性校验解决业务规则问题。不能把安全和流程正确性完全交给 Prompt。

## 为什么追问不能太多

> 用户是懂业务但不懂代码的人。如果把文件格式、分页阈值、重试次数等全部抛给用户，Agent 只是把开发工作转嫁给业务人员。我只让会改变业务结果、权限范围或不可逆影响的问题阻塞流程，其余技术选择由 Agent 给默认值并在方案中透明展示。

## RAG 链路

> 文档先解析并分块，用本地 BGE 中文模型向量化后写入向量存储。查询时取 Top-K 相似片段，将内容、来源 ID、Chunk 和分数一起放入模型上下文。项目还有自建评测集，使用 Hit@K、Precision@K、MRR 和无关问题拒绝率比较阈值，而不是凭肉眼判断检索好不好。

## RAG 与 Tool Calling 的区别

> RAG 是知识注入模式，重点是找到相关资料并进入上下文；Tool Calling 是模型在执行过程中选择某个能力。项目同时使用：主工作流固定执行 RAG，模型还可以按需要调用业务文档和数据库元数据工具。

## MCP 与 Function Calling 的区别

> Function Calling 主要描述模型如何产出结构化工具调用；MCP 解决客户端和外部工具服务之间如何发现能力、协商协议和交换结果。项目内部为低延迟使用 Spring AI `@Tool`，对外通过 MCP Streamable HTTP 复用同类能力，没有让应用通过网络调用自己。

## MCP 安全怎么做

> 只读提示只是元数据，不是真正的权限控制。我关闭了本地工具自动转换，只暴露两个显式 `@McpTool`；服务端还有白名单、500 字参数限制、单轮和单工具调用上限、默认本机监听，以及不记录 Prompt 和结果正文的审计。生产环境仍需要 OAuth、租户身份和持久化审计。

## Trace 与 Evals

> 每个核心节点保存统一 traceId、独立 spanId、状态、耗时和有限属性。聚合层再根据事件和 Span 计算首轮就绪率、平均澄清轮数、推荐值采纳率、完成率、失败率和节点耗时。这样能够区分模型问题、检索问题和流程问题。当前是项目内 Trace，还没有冒充已经接入 OpenTelemetry Collector。

## 为什么不能直接在宿主机运行生成代码

> 文件夹不是安全边界。即使限制路径，生成代码仍可能读取环境变量、访问网络或操作其他文件。因此项目禁止宿主执行，只允许固定 Docker 命令。容器无网络、根文件系统只读，源码和 Maven 仓库只读挂载，并限制 CPU、内存、PID、时间和临时磁盘；Docker 不可用就失败，不做不安全降级。

## 什么是 Autonomy Budget

> 自治预算限制 Agent 最多能生成多少文件和字节、调用多少次构建、占用多少沙箱时间、使用多少 CPU、内存和进程。当前代码任务最多生成 6 个文件、100KB 内容、执行 3 次构建和 180 秒沙箱时间。它不提升模型正确率，但能限制错误规划的成本和影响范围。

## 自动修复循环怎么设计

> 我没有让模型无限自我反思，而是采用 Generate–Test–Repair 循环。Docker 只有明确返回编译或测试失败时才进入修复；修复 Agent 获得上一版完整文件和截断后的失败日志，输出仍要经过结构化 Schema 和 Java 安全策略。修复不能新增、删除或重命名文件，也不能删除测试或放宽断言。最多测试三次，仍失败就进入 FAILED。这叫有界自治，而不是无限重试。

## 为什么代码任务要异步

> 模型生成和容器测试可能持续几十秒，如果占用 HTTP 请求线程，会造成超时、连接浪费和很差的用户体验。创建接口只负责校验并持久化 QUEUED 快照，然后返回 202；固定大小线程池负责后台执行，队列也有容量上限。前端通过任务 ID 轮询状态，后续可以无缝替换成 SSE 或消息队列。

## Checkpoint 与普通日志有什么区别

> 日志主要用于观察发生了什么，Checkpoint 保存继续执行所需的完整状态，例如已审批的工作流输入快照、阶段、补丁、构建次数、累计沙箱耗时、修复轮数、验证结果和事件。项目用 JSON 快照落盘，并通过临时文件加原子替换避免写到一半。应用启动后扫描未完成状态并重新调度，因此恢复不依赖原工作流仓库仍在线。

## 恢复执行如何避免无限消耗

> 构建次数会在真正启动 Docker 之前写入 Checkpoint，所以进程如果在调用期间崩溃，这次预算不会在重启后被返还。恢复时沿用已消耗的构建次数和时间，并使用新的隔离工作区，不覆盖执行上一次的不完整目录。这是保守的至少一次调度语义；因为人工发布前没有外部业务副作用，所以重复生成不会影响真实系统。

## 为什么 Docker 不可用时不自动修复

> 自动修复只适合代码导致的编译或测试失败。Docker 未启动、依赖仓库缺失、路径越界或安全策略拒绝都不是代码缺陷，继续调用模型只会浪费预算，甚至诱导模型绕过安全边界。因此这些异常会直接安全停止并保留 Checkpoint。

## 为什么测试通过后还要审批

> 自动化测试只能证明覆盖到的行为，没有证明需求、安全和代码质量一定正确。因此技术方案审批确认“怎么做”，代码审批确认“实际做了什么”。发布前还会重新计算 SHA-256，避免测试后文件被替换。

## 项目最难的三个点

> 第一是让业务人员少回答问题，所以设计了阻塞决策与默认假设。第二是处理模型不确定性，用结构化输出、Java 校验、状态机、Trace 和评测把不可控部分包起来。第三是代码执行安全，最终放弃宿主进程执行，改成无网络、只读和限资源的容器，并保留人工审批。

## 失败与恢复

> 需求分析、检索或方案生成失败时，工作流进入 FAILED 并保存已有上下文，用户可以在同一 workflowId 上重试。代码阶段保存完整文件 Checkpoint，测试失败会在预算内自动修复；应用启动后自动恢复 QUEUED、GENERATING、VERIFYING 和 REPAIRING 任务。达到预算或遇到基础设施错误后安全停止，绝不会绕过测试发布。

## 当前真实边界

- 数据库工具查询的是演示元数据目录，不读取真实业务行数据。
- 代码只生成到独立演示工程，不直接修改真实存量项目。
- 当前电脑未安装或未配置 Docker CLI，因此容器成功链路尚未在本机完成冒烟；代码明确禁止回退到宿主执行。
- MCP 暂无 OAuth 和租户级授权。
- Trace 尚未导出到 OpenTelemetry Collector。
- 文件 Checkpoint 解决的是单实例恢复，尚未实现 Redis/消息队列、多实例任务租约和分布式抢占。
- 真实 Git 分支与 Pull Request 尚未实现。

面试时主动说出边界不会减分，反而说明你理解 Demo、生产系统和安全声明之间的区别。
