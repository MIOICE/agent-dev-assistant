# Milestone 24：阶段化 Case Skills 与生成溯源

## 为什么要做

如果把所有业务规则都塞进一段系统提示词，模型每一步都会看到大量无关说明，既浪费上下文，也难以回答“本次方案究竟使用了哪套规则”。本阶段将需求澄清与方案审查方法拆成独立、可审核的 Skill，并只在对应阶段加载。

## 实现方式

- `requirement-clarification` 仅在需求分析阶段加载，约束模型优先确认业务对象、操作范围、角色和不可逆规则，每轮最多提出三个阻塞问题。
- `solution-evidence-review` 仅在方案生成阶段加载，要求事实绑定当前客户与 MES 版本的证据，并显式列出假设、风险、测试和回滚。
- Skill 采用带 YAML front matter 的 `SKILL.md`，包含名称、语义版本、阶段和用途说明。
- 应用启动时读取 `manifest.sha256`，逐个校验 Skill 文件；缺失、篡改或清单残留都会阻止启动。
- 自动生成的 `SolutionRevision` 持久化 Prompt 版本与 Skill 清单哈希，人工修订继续继承该来源信息。

## 安全与边界

- Skill 是内部受审的工作方法，不接受用户上传的同名文件覆盖。
- 按阶段最小暴露 Skill，不把历史 Coding Agent 的写文件、测试和修复能力加载进需求方案主流程。
- 版本与哈希只能证明“使用了哪套规则”，不能代替方案内容评测；质量仍需由证据约束、自动评测与人工审批共同保证。

## 验证

- 自动化测试覆盖 Skill 解析、阶段路由和 SHA-256 完整性校验。
- Maven 聚合工程共运行 150 项测试：`case-orchestrator` 107 项、`coding-agent-archive` 43 项，全部通过。

## 面试复述

项目里的 Skill 不是普通提示词文件。我把需求澄清和方案证据审查拆成两个阶段化能力，运行时只加载当前阶段需要的规则，减少无关上下文；启动时用 SHA-256 清单校验完整性，并把 Prompt 版本和 Skill 清单哈希写入每个方案修订版。这样出现坏案例时，可以定位它由哪一版规则生成，再通过固定评测集做回归，而不是凭感觉改 Prompt。
