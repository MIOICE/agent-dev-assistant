# 阶段 19：后台任务运行治理

## 目标

后台 Coding Agent 已经具备 Checkpoint、恢复、SSE 和自治预算，但生产式长任务还需要回答四个问题：重复点击是否会创建重复任务、用户如何停止任务、单次任务最长可以运行多久，以及执行器是否已经拥塞。

本阶段在不引入分布式基础设施的前提下，为单实例运行时补齐这四类控制能力。

## 状态与停止原因

代码任务新增两个终止阶段：

- `CANCELLED`：用户主动撤回任务。
- `TIMED_OUT`：从任务创建开始计算的墙钟期限已经耗尽。

Agent Loop 同时记录独立停止原因 `CANCELLED` 与 `DEADLINE_EXCEEDED`。业务阶段回答“任务最终处于什么状态”，停止原因回答“Agent 为什么停止”，两者不会混为普通异常。

## 幂等提交

`CodingTaskService.submit` 在同步边界内查询同一 `workflowId` 的最新任务。排队中、执行中、等待审批和已发布任务都会被直接返回，不再重复入队。失败、取消或超时任务允许重新创建，满足显式重试需求。

当前幂等边界是单 JVM 加本地 Checkpoint 仓库。多实例部署仍需要数据库唯一约束、任务租约或消息队列的去重能力。

## 协作式取消

取消接口先保存终止 Checkpoint，再由工作线程在以下边界重新检查最新状态：

1. 开始处理任务之前；
2. 模型生成返回之后、写入沙箱之前；
3. 每次 Agent Loop 开始时；
4. Docker 构建返回之后；
5. 修复模型返回之后。

这种方式不会使用 `Thread.stop` 一类不安全机制，也无法强制打断不支持取消的第三方调用。它保证外部调用返回后不再推进状态或产生后续动作。

`approve` 与 `cancel` 使用同一同步边界，防止人工发布和取消同时发生。统一 `save` 方法还会读取仓库最新状态：如果持久化任务已经是 `CANCELLED` 或 `TIMED_OUT`，旧工作线程提交的运行中快照会被拒绝，从而避免终止状态被覆盖。

## 运行期限

`CODING_MAX_TASK_RUNTIME_MS` 控制任务从创建到执行的最长墙钟时间，默认值为 300000 毫秒。排队等待也计入期限，防止拥塞时任务无限滞留。

该期限与 `AutonomyBudget.maxDurationMs` 不同：

- 墙钟期限覆盖排队、模型调用、构建和修复的总生命周期；
- 自治预算统计已记录的沙箱执行耗时与调用次数。

两层预算分别约束系统占用时间和 Agent 自主执行强度。

## 队列运行状态

`GET /api/coding-tasks/runtime` 返回：

- 核心线程数、活跃线程数和当前线程池大小；
- 已排队任务数与剩余队列容量；
- 当前进程正在处理的任务数；
- 单任务最长运行时间。

工作台在代码任务区域展示这些指标，并对可取消阶段提供控制按钮。状态变化继续通过完整 Checkpoint 的 SSE 快照传播；SSE 断线时沿用轮询降级。

## 接口

```text
GET  /api/coding-tasks/runtime
POST /api/coding-tasks/{taskId}/cancellation
```

取消请求体示例：

```json
{
  "reason": "业务需求已撤回"
}
```

## 验证范围

自动化验证覆盖重复提交去重、排队任务幂等取消、取消后旧执行入口不再推进、恢复任务超时、控制接口、执行器状态接口和前端入口。全项目当前通过 132 个自动化测试。

## 当前边界

- 取消是协作式而非抢占式，第三方调用返回前线程仍可能处于等待状态。
- 运行状态来自当前 JVM，不是跨实例集群视图。
- 本地文件 Checkpoint 不提供跨实例 compare-and-set；多实例部署需要外部协调存储。
- 队列指标用于运行观察，尚未接入告警、自动扩缩容或持久化消息队列。
