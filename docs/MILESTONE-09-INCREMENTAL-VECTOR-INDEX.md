# 里程碑 09：持久化快照与增量向量索引

## 本阶段解决了什么

里程碑08接入237份MES文档后，每次启动都要对3311个Chunk重新调用本地BGE，冷启动约36秒。即使文档没有变化，计算仍会完整重复。本阶段在现有`SimpleVectorStore`外增加可恢复的索引生命周期：

```text
当前Chunk
  -> 计算ID、正文、元数据SHA-256
  -> 读取磁盘manifest与向量快照
  -> Schema或modelId不兼容：全量重建
  -> 清单损坏：安全恢复重建
  -> 指纹完全一致：WARM_LOAD，直接复用全部向量
  -> 指纹有差异：INCREMENTAL_UPDATE
       ├─ 新增Chunk：计算并add
       ├─ 修改Chunk：delete旧ID，重新计算并add
       └─ 删除Chunk：delete旧ID
  -> 临时文件写入 + 原子替换正式快照和清单
```

## 为什么使用Chunk指纹

只比较文件修改时间不可靠：复制文件可能改变时间但内容不变，不同文档也可能最终生成相同数量的Chunk。系统实际参与检索的是Chunk，因此指纹覆盖Chunk ID、正文和排序后的元数据。只要检索语义或引用信息发生变化，对应指纹就会变化。

清单还保存Schema版本和`KNOWLEDGE_INDEX_MODEL_ID`。更换Embedding模型、Tokenizer或预处理规则时，即使文档完全不变，旧向量也不能继续使用；修改模型标识会触发`INCOMPATIBLE_REBUILD`。

## 持久化与失败恢复

索引由两个文件组成：

- `vector-store.json`：Spring AI `SimpleVectorStore`快照，包含向量、Chunk文本和元数据；
- `manifest.json`：模型标识、语料总指纹和每个Chunk指纹。

保存时先在相同目录生成随机临时文件，再通过原子移动替换正式文件。缓存不存在时进入`COLD_REBUILD`；JSON损坏或加载异常时进入`RECOVERED_REBUILD`。前端和`GET /api/knowledge/index/status`会展示模式、复用、新增、更新及删除数量。

## 本轮真实验证

- 外部237份与内置3份文档共生成3311个Chunk；
- 首次构建生成约25.3MB向量快照和452KB指纹清单；
- 第二次启动进入`WARM_LOAD`，复用3311个向量，新增、更新、删除均为0；
- 两次热启动实测为14.63至15.36秒，相比原约36秒缩短约58%；
- 热加载后12条RAG回归评测仍全部通过；
- 累计89个自动化测试通过，覆盖冷构建、热加载、增删改、模型版本失效、缓存关闭和损坏恢复。

剩余约15秒主要用于Spring容器、Tokenizer和本地BGE模型初始化。磁盘快照避免的是语料向量重算，并不会让查询模型无需加载。

## 为什么暂时不直接上Qdrant

当前规模只有3311个Chunk，运行形态是单机演示，核心瓶颈是重复Embedding。引入Qdrant会增加服务、端口、Volume和部署复杂度，但不能消除本地BGE模型初始化。先用Spring AI现有快照能力解决真实瓶颈，同时将索引管理与检索调用分离；当需要多实例、服务端过滤、在线扩容和高并发时再替换独立向量数据库。

## 面试复述版本

> 接入真实MES语料后，我发现3311个Chunk每次启动都会重新向量化，冷启动约36秒。我没有马上堆Qdrant，而是在SimpleVectorStore外设计Chunk级增量索引：对ID、正文和元数据计算SHA-256，通过清单识别新增、更新和删除，只对变化Chunk重新Embedding；语料不变时直接加载磁盘向量快照。模型标识或Schema变化会强制重建，缓存损坏也会安全回退重建。实际热启动复用3311个向量，重算为0，两次实测14.63至15.36秒，缩短约58%，RAG评测结果保持不变。

## 本阶段简历可写版本

- 针对237份MES文档、3311个知识Chunk每次启动重复向量化的问题，基于Spring AI `SimpleVectorStore`设计磁盘向量快照与Chunk级增量索引，通过SHA-256清单识别新增、修改和删除内容，仅对变化Chunk重新Embedding。
- 引入索引Schema与Embedding模型版本校验、损坏缓存安全重建，以及临时文件加原子替换机制；通过状态接口和前端展示冷构建、热加载、复用及增删改数量。
- 本机热启动复用3311个向量、重算为0，两次实测14.63至15.36秒，相比原约36秒缩短约58%；热加载后12条RAG回归评测全部通过，累计89个自动化测试通过。

## 当前真实边界

- `SimpleVectorStore`快照是单机JSON持久化，不是独立向量数据库。
- 向量快照包含经过基础脱敏的Chunk文本和元数据，不能公开提交，也尚未实现静态加密。
- 当前没有多进程/多实例写锁、索引蓝绿切换和租户隔离。
- 文档读取与标题分块仍会在每次启动发生，避免的是Embedding重算。
- `modelId`由配置显式维护，修改Embedding模型或预处理规则时需要同步提升版本。
