# 检索优化设计

## 问题

MES 资料具有三个典型特点：业务缩写和专有名词多、同一功能在不同版本中实现不同、单条客户需求往往同时涉及流程/权限/数据/风险。只执行一次向量查询容易遗漏精确术语，也可能把其他客户或版本的相似资料当作事实。

## 检索链路

### 1. 查询拆解

Java 编排端最多生成五个调查问题：客户原始需求、主要影响模块及高风险约束。模型只参与“找什么”，不能决定证据是否可信，也不能扩大查询预算。

### 2. 元数据前置过滤

Python Agent 在检索前按 `tenant_id + system_id + system_version` 选择唯一知识空间。没有精确匹配时直接返回 `sufficient=false`。过滤发生在检索之前，而不是在 Prompt 中提醒模型“不要看其他客户”。

### 3. 双路召回

- 语义路：使用 Embedding 在指定知识空间内召回候选，适合自然语言改写和近义表达。
- 关键词路：从标题和 Chunk 正文提取英文/数字 Token 与中文二元词，适合锁批、工序代码、接口名等精确术语。

关键词候选设最低覆盖阈值，避免仅含一个通用词就进入结果。

### 4. RRF 融合

语义余弦分与关键词覆盖率不在同一尺度，不能直接相加。系统按排名使用 Reciprocal Rank Fusion：

```text
RRF(d) = 1.0 / (60 + semantic_rank) + 0.9 / (60 + lexical_rank)
```

同时命中两路的 Chunk 会自然前移；只有关键词命中的专有术语资料也能被召回。最终每份文档最多保留两个 Chunk，避免单一来源占满上下文。

### 5. 覆盖度和拒答

Java 对跨问题结果按 `chunkId` 去重，并保存每个问题命中的 ID。任何必要问题未命中，或证据被租户/版本/提示注入策略隔离，Case 进入 `EVIDENCE_INSUFFICIENT`，不会编造方案事实。

## 可观测字段

每条证据保存来源文件、documentId、chunkId、chunkIndex、systemVersion、spaceKey、`semanticScore`、`lexicalScore` 与 `retrievalSources`；证据包还保存每个调查问题的命中 ID 和未解决问题。

这些字段用于定位“向量没召回、关键词没匹配、版本空间错误还是后置策略拦截”。

## 测试与评测

当前自动化测试验证：

- 当向量路完全漏召回时，关键词路可恢复 MES 专有术语；
- 每份文档结果数量不会超过预算；
- A2A 返回的证据严格属于令牌中的 tenant；
- 其他 tenant 不能读取已有 A2A Task。

完整效果数据必须来自不少于 80 条人工审核的脱敏案例，并分别报告 Hit@K、MRR、引用正确率、无答案拒答率和跨租户泄漏数。在人工评测完成前，不在简历填写虚构百分比。
