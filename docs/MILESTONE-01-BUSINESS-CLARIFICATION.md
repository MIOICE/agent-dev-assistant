# 里程碑 01：业务友好澄清 Agent

## 解决的问题

旧版本把模型产生的所有 `missingInformation` 都视为阻塞条件。技术选型、展示偏好和真正影响业务结果的问题混在一起，业务用户需要连续输入大量文字，形成“问题爆炸”。

本轮把澄清过程改成结构化决策：

- 每个问题包含类别、问题、选项、推荐值和 `blocking` 标记。
- 只有业务范围、权限边界和不可逆操作等关键未知信息可以阻塞流程。
- 文件格式、分页、异步阈值、重试和日志等内容使用推荐默认值，记录到 `assumptions`。
- Java 校验层对模型结果去重、补全推荐选项，并把阻塞问题限制为最多 4 个。
- 前端支持单选回答和“一键采用推荐方案”；确认结果进入原工作流上下文和事件历史。

## 面试时怎么复述

> 我发现单纯依赖大模型判断信息是否完整，会把很多技术细节也变成用户必须回答的问题。于是我把澄清建模为结构化对象，由模型负责语义识别，再由 Java 策略层做确定性约束：只有影响业务结果、权限或不可逆操作的问题才能阻塞流程，每轮最多 4 个；其余技术选择转成显式假设。前端允许业务人员点选答案或一键采用推荐值，确认后继续同一个可恢复工作流。这个设计属于 Context Engineering、Structured Output、Policy Guardrail 和 Human-in-the-loop 的组合。

追问时可以说明：模型擅长理解自然语言，但不适合独自决定生产流程边界；确定性 Java 规则用于兜底可控性，用户确认用于承担业务决策。

## 本轮验证

- `mvn test`：50 个测试全部通过。
- Mock 端到端冒烟：模糊“增加导出功能”只产生 1 个阻塞业务问题；一键采用推荐值后保留同一 `workflowId`，进入 `WAITING_APPROVAL` 并生成技术方案。
- 页面资源检查：结构化问题渲染、一键推荐按钮和默认假设区域均已加载。

## 本轮简历可写版本

项目名称：面向企业存量系统的需求开发 Agent

- 基于 Java 21、Spring Boot、Spring AI 与 DeepSeek 构建企业需求开发 Agent，将自然语言需求转化为结构化需求卡片，并串联业务知识检索、技术方案生成与人工审批工作流。
- 针对业务用户澄清成本高的问题，设计包含类别、候选项、推荐值及阻塞等级的结构化澄清机制；通过 Java 确定性策略完成问题去重、默认值修复及阻塞问题上限控制，支持逐项选择与一键采用推荐方案。
- 将业务范围、权限边界及不可逆操作作为阻塞决策，将分页、异步阈值、重试与日志等技术选择沉淀为可审阅假设，结合同一 `workflowId` 的状态恢复和事件记录实现 Human-in-the-loop 闭环。
- 使用 JUnit 5、MockMvc、H2/MySQL 兼容测试验证需求分析、RAG、Tool Calling、持久化和状态迁移，当前累计 50 个自动化测试全部通过。

注意：简历中暂时不要写“真正实现 MCP、自动改代码、Redis、生产发布”，这些能力还没有完成。
