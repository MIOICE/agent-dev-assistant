# 阶段 11：方案证据绑定与未支撑结论检测

## 要解决的问题

Agentic RAG 已经能够记录“应该找什么、找到了什么、还缺什么”，但技术方案此前只在末尾附一串参考资料，仍有三个问题：

- 无法知道某条数据库、安全或性能结论具体依据哪个 Chunk；
- 模型可能生成与检索资料无直接来源关系的工程结论；
- 待确认假设和事实性结论混在一起，人工审批成本仍然较高。

本阶段新增独立 Grounding 节点，把技术方案拆成原子结论并建立可验证的来源关系。

## 数据模型

每条 `GroundedSolutionClaim` 保存：

- 稳定 `claimId`、方案章节和序号；
- 原始结论文本；
- 关联的最终证据 Chunk ID；
- `EVIDENCE_LINKED`、`ASSUMPTION` 或 `UNSUPPORTED` 状态；
- 面向用户的状态说明。

`SolutionGroundingReport` 汇总事实性结论数、证据关联数、假设数、未支撑数和证据关联率，并保留安全边界提示。

## 绑定规则

```text
摘要              -> 当前证据计划命中的代表性 Chunk
后端流程          -> BUSINESS_RULES
数据库 / API      -> DATA_AND_API
安全控制          -> SECURITY
性能策略          -> PERFORMANCE
测试 / 回滚       -> 与需求相关的全部证据目标
待确认项          -> ASSUMPTION，不伪造引用
```

模型规划的 ID 不完全一致时，系统还会根据证据目标的查询和目的识别业务、数据、安全和性能语义。所有引用必须再次通过最终证据 ID 白名单；已被证据去重或截断掉的 ID 不能进入方案引用。

## 工作流集成

方案生成完成后执行 `agent.solution-grounding` 节点，再进入人工审批。报告随不可变 `WorkflowState` 保存到内存或 MySQL JSON 快照，包含关联率和未支撑项数量的 Trace 属性。

人工驳回后，系统使用反馈重新生成技术方案，并对新方案重新执行 Grounding，避免旧引用污染新版本。

## 验证结果

- 验证数据库结论只绑定 `DATA_AND_API` 实际命中的 Chunk；
- 验证安全证据未命中时，安全结论被标记为 `UNSUPPORTED`；
- 验证假设不计入事实性结论和关联率分母；
- 验证工作流新增独立 Grounding Span，并在重新生成后更新报告；
- 验证空 Grounding 字段能够归一化为空报告并完成 Checkpoint 序列化；
- 全项目 94 个自动化测试通过，前端 JavaScript 语法检查通过。

## 面试复述

> 我没有把“RAG 返回了几条结果”直接当成方案可信。方案生成后会进入独立 Grounding 节点，把摘要、后端、数据库、API、安全、性能、测试和回滚拆成原子结论，再根据证据计划和实际命中的 Chunk ID 建立来源关系。引用 ID 必须存在于最终证据集合；没有专项证据的结论标成 UNSUPPORTED，待确认内容标成 ASSUMPTION，关联率排除假设。这样人工审批可以直接定位高风险结论，方案驳回重生成后也会重新绑定。

## 简历可写版本

> 构建技术方案 Grounding 与来源追踪机制，将后端、数据库、API、安全、性能等方案结论逐项绑定至 Agentic RAG 实际命中的 Chunk，并通过最终证据 ID 白名单剔除无效引用；区分 `EVIDENCE_LINKED`、`ASSUMPTION` 与 `UNSUPPORTED`，计算排除假设后的证据关联率，结果随工作流快照持久化并在方案重生成后自动更新。

## 当前边界

- 当前验证的是来源存在性和证据类别覆盖，不是自然语言蕴含证明。
- `EVIDENCE_LINKED` 只能解释为“关联到相关检索来源”，不能包装成“事实正确率”。
- 尚未使用 NLI/LLM Critic 检查证据是否支持或反驳具体结论，也没有 claim–evidence 人工金标集。
- 证据关联率是可观察性指标，不应与最终方案准确率混为一谈。
