# 阶段 15：自适应业务澄清

## 要解决的问题

企业需求的原始输入通常来自熟悉业务但不了解代码的人。如果把模型想到的字段、权限、格式、分页、线程池和重试问题一次性全部展示，用户会感到复杂，也无法判断技术问题。

项目早期已经支持结构化选项和推荐值。本阶段进一步增加确定性问题路由，让系统回答三个问题：

- 哪些必须由业务人员决定？
- 哪些可以由Agent结合规范采用安全默认值？
- 本轮最值得先确认的是哪2至3项？

## 数据结构

`ClarificationQuestion` 在原有类别、问题、选项、推荐值和阻塞标记之外，新增：

- `reason`：为什么必须询问；
- `impact`：不同选择会影响哪些业务结果、安全边界或验收内容。

旧代码的五参数构造器和历史JSON仍然兼容；缺失的解释会由Java策略按问题类别补全。

## 自适应路由

`AdaptiveClarificationPolicy` 执行以下步骤：

```text
模型候选问题
  -> 去重、修复选项与推荐值
  -> 技术实现词识别
  -> 技术问题降级为Agent假设
  -> 按不可逆操作、权限、范围、字段、时效排序
  -> 选择最高风险的3个业务决策
  -> 其余有安全推荐值的问题转为显式假设
  -> 无推荐值的问题继续阻塞，不因数量预算被静默跳过
```

当前技术问题词表覆盖线程池、索引、重试次数、分页大小、批次大小、超时、缓存、消息队列、异步阈值、接口协议、数据库类型和代码结构。

风险排序优先级不是模型自报分数，而是Java根据类别和关键词计算：删除、不可恢复、越权和敏感数据最高，其次是权限角色、全量与批量范围，再到字段、时效和普通偏好。

## 与模型和工具的分工

- DeepSeek负责理解自然语言、调用业务文档和数据库元数据工具、生成候选问题及解释；
- Java负责问题去重、业务/技术分流、风险排序、每轮问题预算和安全兜底；
- 能从工具资料、现有权限或当前页面规则确定的信息进入`assumptions`；
- 人工只负责会改变业务结果、权限边界或不可逆影响的选择。

这种设计比完全依赖Prompt稳定，因为模型即使错误地把技术问题标成阻塞，Java仍会做第二层路由。

## 前端体验

等待澄清时，页面展示：

- “本轮需确认N项”和“Agent已处理N项”；
- 每个问题的类别、提问原因和决策影响；
- 2至4个业务选项和推荐标记；
- 可展开的“Agent已处理的默认决策”；
- 逐项选择或一键采用全部推荐值。

工作流事件和Trace同时记录用户问题数、Agent默认数和具备完整解释的问题数。

## 验证

- 验证技术实现问题自动转为Agent默认；
- 验证删除、权限和全量范围优先于时效及界面偏好；
- 验证每轮通常最多三个阻塞业务问题；
- 验证无安全推荐值的问题不会被静默跳过；
- 验证推荐值自动加入选项；
- 验证所有问题补齐原因与影响；
- 验证Mock分析器同样经过确定性问题路由；
- 验证前端展示原因、影响和默认决策；
- 全项目114个自动化测试通过。

## 面试复述

> 为了让懂业务但不懂代码的用户使用，我没有把模型生成的问题全部展示，而是在模型后增加确定性问题路由器。它先把线程池、索引、分页、重试等技术问题转成可复核假设，再按删除、权限和数据范围等业务风险排序，每轮只让用户确认最高价值的三项。每题解释为什么问以及会影响什么，并提供推荐值。没有安全默认值的问题不会因为数量限制被跳过，所有Agent默认也会显式展示并进入后续人工审批。

## 简历可写版本

> 设计面向非技术业务人员的自适应需求澄清机制，在模型候选问题后增加Java确定性路由，识别并降级线程池、分页、重试等技术问题，按不可逆操作、权限及数据范围进行风险排序，每轮优先呈现2至3项关键业务决策；为问题补充原因、影响及推荐值，并显式保留Agent默认假设供后续审批复核。

## 当前边界

- 技术问题识别目前使用可审计词表，不是完整的业务意图分类器；
- 问题路由尚未单独建立人工金标评测集；
- Agent从知识库推断的信息仍以模型工具调用结果为基础，没有实现字段级置信度校准；
- 多轮澄清依赖重新分析完整需求上下文，尚未拆成独立的对话状态图；
- 默认假设会展示并进入技术审批，但尚未提供逐项撤销默认值的专用接口。
