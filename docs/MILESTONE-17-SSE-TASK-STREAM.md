# 阶段 17：SSE 实时代码任务状态流

## 要解决的问题

代码生成、Docker 测试和自动修复属于长任务。项目此前由浏览器每 1.2 秒请求一次任务接口，虽然简单可靠，但存在三个问题：

- 即使状态没有变化也会持续发送请求；
- 短暂步骤可能在两次轮询之间发生，用户只能看到最终结果；
- 无法直观表达服务端正在主动推进 Agent Loop。

本阶段使用 Server-Sent Events 将持久化后的最新任务快照实时推送到工作台，并保留轮询作为兼容降级。

## 为什么选择 SSE

当前实时链路主要是服务端向浏览器单向推送：

- 用户提交、审批等操作继续使用普通 POST；
- 服务器只需要推送任务阶段、Loop 步骤、构建和停止状态；
- 浏览器原生 `EventSource` 支持自动建立长连接和断线重连；
- 相比 WebSocket，不需要额外的双向消息协议和连接状态机。

## 服务端设计

`GET /api/coding-tasks/{taskId}/stream` 返回 `text/event-stream`。

`CodingTaskEventStream` 为每个任务维护本机订阅者列表：

1. 验证任务存在；
2. 注册 `SseEmitter`，超时为 5 分钟；
3. 注册完成、超时和异常清理回调；
4. 从 `CodingTaskRepository` 读取最新完整快照并立即发送；
5. 后续每次任务保存后发布 `coding-task` 命名事件；
6. 单个客户端发送失败时只移除该连接，不改变任务状态。

SSE 事件 ID 由更新时间、事件数量和 Agent Loop 步骤数组成，便于浏览器和日志定位。

## 为什么推送完整快照

系统没有要求客户端从第一条事件开始完整消费增量日志。真正的事实来源是 `CodingTaskRepository` 中的 Checkpoint：

```text
Agent状态变化
  -> 原子保存完整CodingTask
  -> SSE广播最新完整快照
  -> 浏览器直接替换页面状态
```

断线期间即使漏掉生成和第一次测试事件，重连时也会收到包含完整事件、构建记录和 Agent Loop 轨迹的最新状态。

订阅建立与后台保存可能并发。每个客户端保存最近发送的 `updatedAt`，较旧快照不会覆盖较新状态，避免重连初始快照和实时推送乱序。

## 前端设计

- 活跃任务优先建立 `EventSource`；
- 页面显示“SSE 连接中”或“SSE 实时”；
- 收到 `coding-task` 后解析完整 JSON 并重新渲染；
- 任务进入审批、失败或发布状态后关闭连接；
- 浏览器不支持 SSE、连接异常或数据解析失败时，显示“轮询降级”并每 1.5 秒读取一次任务；
- 下一次成功读取后会再次尝试建立 SSE。

## 可靠性边界

- 先持久化再推送，页面看到的状态必然已经存在于 Checkpoint；
- SSE 不是任务执行依赖，客户端全部断开也不影响 Agent；
- 快照事件具有幂等展示语义，重复接收不会重复执行任何动作；
- 连接列表使用线程安全集合，慢客户端或断线客户端会在发送异常、完成或超时时清理。

## 验证

- 新订阅立即收到最新任务快照；
- 更新后的快照可以推送到相同任务订阅者；
- 并发到达的旧快照不会覆盖新状态；
- 断线订阅者会被移除，任务发布不抛出异常；
- 控制器声明 `text/event-stream`；
- 前端包含 EventSource、实时状态标识和轮询降级；
- 前端 JavaScript 语法校验通过；
- 全项目 121 个自动化测试通过。

## 当前边界

- 订阅者列表位于单机内存，多实例部署需要 Redis Pub/Sub、Kafka 或其他消息总线；
- 当前没有用户身份和每用户连接数限制；
- 没有额外心跳事件，依赖状态更新、Emitter 超时和浏览器重连；
- 发送仍发生在任务保存调用线程，当前本地连接量很小；高并发场景应增加异步广播队列和慢消费者隔离；
- SSE 只推送状态，不承载审批、取消或终端输入等双向指令。
